# 記事公開スキル(配信者)

> **【ルール本体は`.claude/agents/publisher.md`が正】** 詳細な手順・判定基準・出力フォーマットは`.claude/agents/publisher.md`を参照すること。**このファイルとpublisher.mdの記述が食い違った場合は、常にpublisher.mdを正としてこのファイル側を修正する。**

## 記事が公開される経路(このスキルは新規公開を行わない)

記事の状態は 作成中 → 公開待ち → 公開済み の3種類。作成中: 企画を始めた時点で `サイト運営\記事データ\作成中\<日付>_<記事名>\` を作り、企画書・原稿・確認メモ・判定の記録・画像のプロンプトをすべてここに置く(最後の判定が終わるまで、ここから動かさない)。公開待ち: 最後の判定を通った公開する版の1ファイルだけを置く(`publishAt` を入れる。判定を通っていない原稿は置かない)。公開済み: 公開の処理(公開キュー、または手動の実行)だけが公開待ちから移す(担当が新しい記事を手で置かない)。公開したあとは、作成中のその記事のフォルダを消す(画像のプロンプトなど、あとで要るものは、消す前に報告へ出す)。公開済みの記事を直すときは、公開済みの同じファイルを直す(公開待ちは通さない。大きく作り直すときは、作成中に作業用のフォルダを作り、できた版で公開済みの同じファイルを置き換える)。判定を通らなかった記事・公開を取りやめた記事は、公開待ちにも公開済みにも置かず、作成中に残すか `非公開アーカイブ\` へ移す。正本は `.claude\skills\run-article-production\SKILL.md` の「記事の状態と置き場」。

新規記事は、判定を通過して `記事データ\公開待ち\` に置かれ、公開の時刻(`publishAt`)が `npm run queue`(割り振りの仕組み)などで入り、GitHub Actions(`.github\workflows\publish-queue.yml`)が `scripts\queue-release.js` を動かして、公開時刻の到来した記事を `記事データ\公開済み\` へ移してcommit・pushする。pushでVercelが自動デプロイし、そこで初めてサイト・sitemapに出る。

このスキルの担当は、(a) 既に公開済みの記事に加えられた修正をサイトへ反映すること、(b) 公開後のPinterest追記・ピン画像作成 の2つである。新規記事の公開を依頼された場合は、作業を行わずにユーザーへ報告し、上の経路を案内する。

**公開の決まり(2026-10-12 依頼者の決定。2026-10-11 の「公開は待たない」を改めた)**:

- **ア. 依頼者が「すぐ公開」と指定した記事(1本でも複数でも)**: 公開の時刻(`publishAt`)を今の時刻以前にして、公開待ちに置く。commit して push したあと、公開の処理を手動で実行する(GitHub Actions の `publish-queue.yml` を手動で実行する。または手元で `node scripts/queue-release.js` を実行し、移ったファイルを名前を指定して commit・push する)。本番でその記事が表示されることを確かめて、報告する。
- **イ. それ以外の記事(指定が無い。複数の記事をまとめて作る場合を含む)**: 予約投稿にする。公開の時刻は、割り振りの仕組み(`npm run queue`。`scripts/queue.js`・`queue-schedule.js`)で決める。担当が手で決めない。公開待ちに置いて、commit して push する。そこで終わる。公開は自動処理(`publish-queue.yml` の予約実行)に任せる。公開されるのを待たない。手動でも実行しない。報告に、記事ごとの予約した時刻と、「公開後の確認は未実施」と書く。
- 「記事の状態と置き場」の決まりは変わらない。
- 手順の全文は `.claude/agents/publisher.md` の「公開の決まり」。公開ゲートの台帳(`publish-gate.js`)は、このサイトに今ない。公開前の確かめは publisher.md の「公開前の確かめ」。

## 反映の前提(ゲート、詳細はpublisher.md参照)

`記事データ\公開済み\`配下の記事をcommit・pushする前に、`node scripts/verify-article.js "<対象記事の絶対パス>"` を必ず実行する。**目視での「合格しているはず」という推測でゲートを通さない。**

- 実行そのものは必須で、`overall=No`の記事は公開せず、直してから公開する(publisher.mdの「公開前の必須確認(ゲート)」節参照)。信頼性系ブロッキング違反(item10/11/12等)が公開済みの記事に見つかった場合は即時修正が原則、修正に時間を要する場合の非公開化は**必ずユーザー決裁を経る**(`docs/CONTRIBUTING.md` 26節(b))
- 実行結果のJSONは `docs/pipeline/verify/{slug}_{実行日 YYYY-MM-DD}.json` に保存する

## 反映の流れ(概要)

1. `git status` で `サイト運営\記事データ\公開済み\` 配下に未コミットの変更が無いか確認する
2. 変更があれば、内容(記事タイトル・変更概要)を報告に書いたうえで、確認を待たずに該当ファイルを明示的に指定して`git add`→`git commit`(記事タイトルを含むメッセージ)
3. `git push`の前に、依頼者の確認は取らない(2026-10-03 依頼者の決定)。公開の手順(最後の関門の表・publisher.md の「公開前の確かめ」)を満たしたら push する
4. push後、Vercel側の自動デプロイ完了を確認する(反映確認は最低5分待つ、`CLAUDE.md`のデプロイ運用ルール参照)

## サイト未実装の場合

`サイト運営\サイト本体\`にNext.jsプロジェクトがまだ存在しない場合は、作業を中断し、`site-engineer`による最低限の実装を先に依頼するようユーザーに案内する。

## エラー時

git操作やビルドが失敗した場合、エラーメッセージをそのまま報告し、憶測で原因を断定しない。原因調査が必要な場合はincident-responderへの依頼を提案する。先行 commit で弾かれた場合の取り込み方は CLAUDE.md のデプロイ運用ルールのとおりにし、行ったことを報告する。
