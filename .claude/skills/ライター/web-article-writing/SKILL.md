# Web記事執筆スキル(ライター)

## frontmatter
記事Markdownの冒頭に以下を必ず含める。
```yaml
---
title: "SEOキーワードを含むタイトル"
description: "検索結果に表示される120字程度の要約"
category: "対象ジャンルのカテゴリ(例: 制作時に指定)"
tags: ["キーワード1", "キーワード2"]
affiliateLinks:
  - label: "紹介する商品・サービス名"
    url: "アフィリエイトリンクURL"
---
```
提携先が未整備の場合は `affiliateLinks` 自体を省略する(空配列やプレースホルダー文言を残さない)。`label`/`url`以外のキー名(`name`等)を使うと `/compare` ページのビルド時に値が`undefined`になりビルドエラーになるため、キー名は必ずこの2つで統一する。

## 執筆前チェック(必須)
書き始める前に次の2点を確認する。手戻りを防ぐための最初のゲート。

**検索意図分析**
- 検索者が本当に知りたいことは何か(表面的なキーワード一致ではなく目的ベースで考える)
- 初心者が最初に知りたい情報は何か
- それを読んだ後、次に何を疑問に思うか(その疑問まで記事内で解決できているか)
- 1記事1検索意図が原則。複数意図が混じる場合は無理に詰め込まず、対象外の意図は別記事候補としてproject-manager・分析者に申し送る

**記事重複防止**
- `サイト運営\記事データ\確定稿\` と `公開済み\` を Glob/Grep で確認し、同じ検索意図・似たタイトル/見出し構成の既存記事がないかチェックする
- 似たテーマが既にある場合は、対象読者・検索意図・解決する悩みのどれかを明確に変えて差別化する(同じ説明の繰り返しにしない)

## 文章トーン
専門的な内容でも、論文・教科書・説明書のような硬い文章にしない。**読者に一方的に説明する専門家」ではなく、「信頼できる案内役」として書く。**
- 難しい言葉は初回登場時に簡単な説明を添える
- 専門用語を連続させない
- 一文を長くしすぎない(「段落の長さ」参照)
- 読者への語りかけを適度に入れる(「〜って思ったことありませんか?」等)
- 初心者でも理解できる表現にしつつ、幼稚になりすぎない
- 口調はくだけた話し言葉寄りにする。「です・ます」の説明口調・堅い敬語を並べず、友人に話すようなトーンを基本にしつつ、記事全体の信頼性を損なわない範囲に留める
- 文末表現に必ずバリエーションを持たせる。同じ文末が3回以上連続すると単調になる

## 執筆の型(記事設計の流れ)
1. **タイトル**: SEOキーワードを含む
2. **導入文**: 読者の悩み・検索意図への共感から入る。専門用語や前置き、一般論から始めない
3. **この記事で分かること**: 💡ポイントで要点を先出しする(下記「見出しラベル」参照)
4. **マスコット登場**(必須): 「こんにちは、〇〇だよ〜。今日は〇〇のお話をするね。」のような自己紹介+本記事テーマの一言で読者を迎える(下記「マスコットキャラクターの使い方」参照)。サイトの世界観づくりの要なので省略しない
5. **本文(見出しH2/H3)**: 想定検索キーワードを含む見出しで本論を構成する。データや理由を"会話的"に触れ、数値の羅列にしない。**分析者が特定した「競合記事の弱点・不足点」を踏まえ、その記事にしかない切り口や情報を早い段階で示す**。核となる具体的事実(数字・固有の条件・期間など)は各見出しに最低1つは残す
6. **比較表・グラフ・具体例**: 「図表・データ活用」参照
7. **アフィリエイトリンク配置**: 文脈に沿って自然に商品・サービスを紹介する箇所に配置し、広告表記(PR/広告等)を明記する
8. **重要ポイント整理**: 箇条書き・表で要点をまとめる
9. **まとめ**: 記事の要点と、次の行動(比較ページ・ランキングページ・商品ページ等への導線)を示す。テンプレ的な汎用フレーズで終わらせず、本文の具体的内容に紐づいた結論にする
10. **マスコットの締めコメント**(任意): 「つまり〇〇ということだよ!」のような一言で読後感を後押しする

## 段落の長さ
1段落に3文以上を詰め込まない(目安2〜3文、長くても4文まで)。話題や視点が変わる箇所(「そもそもの原因」→「対策」、「一般論」→「私の体験」など)では必ず段落(空行)を分ける。1文が長い場合も、読点の多い一文をだらだら続けず、意味の区切りで文自体を分割する。読者がスマホの狭い画面で読む前提で、圧迫感のある「文字の壁」を作らない。

## AI感を避けるルール
- 「〜と言われています」「〜というデータも」を1記事内で2回以上使わない
- 一人称・実体験ベースの語り口を優先する(「〜って気づいた」「〜してみようと思う」)
- 断定的な効果表現は避けつつ、ヘッジ表現(個人差があります等)を連発しない。1箇所にまとめる
- 数値データを羅列せず、必要な範囲に絞って触れる

## 「読まれる・上位表示される」ための必須チェック
- ヘッジ表現で具体性を薄めすぎていないか。法務上必要な最低限のヘッジは残しつつ、それ以外まで曖昧にして当たり障りのない記事にしない
- 分析者が特定した競合記事の弱点を、自社記事で実際に埋められているか
- 読み終えたときに「この記事は他と違って役に立った」と思わせる一点があるか。なければ書き直す

## マスコットキャラクターの使い方
マスコットは単なる挿絵ではなく、読者理解を助ける案内役として使う。**本文全体をキャラクター口調にするのは禁止。基本文章は通常の読みやすい記事形式にし、要所でキャラクターが補足する形式にする。**

本文Markdown中に次の記法を書くと、その場所にカテゴリ担当マスコット(`lib/categoryMascot.js`、全9カテゴリ対応済み)の吹き出しが挿入される。

```
:::mascot
ここにマスコットのセリフを1〜3文程度で書く。
:::
```
- 前後に必ず空行を入れる。他の段落・リスト・引用ブロックの内側には書かない(ブロックとして認識されなくなる)
- 使う箇所の目安: **記事冒頭の導入直後(必須)・難しい内容の補足・重要ポイントの整理・注意事項・まとめ**。冒頭以外は入れる場所を絞り、自然な箇所だけに使う
- **記事冒頭は必ずマスコットの自己紹介+挨拶から始める**。「こんにちは、〇〇だよ〜。今日は〇〇のお話をするね。」のように、名前を名乗った上でテーマに軽く触れる一言にする(サイトの世界観・ブランド体験を作る役割のため省略不可)
- 1記事あたり目安3〜5箇所まで(冒頭を含む)。詰め込みすぎると本文の読みやすさ・専門性を損なうので避ける
- セリフは各キャラクターの一人称・語尾(「〜だよ」「〜してみてね」等)に合わせる。キャラクター名・口調は`categoryMascot.js`の該当カテゴリを参照する
- 図表の前後で使う場合の例:
  - 表の前: `:::mascot\n比較するときは、この3つの違いを見るのが大事だよ!\n:::`
  - 表の後: `:::mascot\nつまり、自分の目的に合ったものを選ぶのが一番なんだよ。\n:::`
- 冒頭で使う場合の例: `:::mascot\nこんにちは、マドカだよ〜。今日は一人暮らしの布団乾燥機選びについて、一緒に見ていくね。\n:::`
- 旧方式のfrontmatter`mascotComment`(本文中央のH2直前に1箇所だけ自動挿入)は後方互換のフォールバックとして残っているが、**新規記事では本文中の`:::mascot:::`を基本とする**(`:::mascot:::`を1つでも書いた記事では`mascotComment`側の自動挿入は行われない)

## 見出しラベル(💡ポイント等の記号運用)
読みやすさ向上のため、要点・注意・まとめ等は統一した記号ラベルで揃える。装飾目的で絵文字を連発しない。

▼悪い例▼
```
✨💡🌟おすすめポイント🌟💡✨
```
▼良い例▼
```
💡ポイント
○○を選ぶ際は、価格だけでなく成分も確認しましょう。
```

用途別の目安ラベル(1記事内で表記を統一する):
- `💡ポイント` : 重要な要点
- `⚠️注意` : 注意事項・デメリット
- `✅まとめ` / `✅チェック` : まとめ・チェック項目

## 本文の装飾記法
サイト側のMarkdown処理(remark-gfm対応済み)で以下が使える。多用しすぎず、本当に強調したい1〜2箇所に絞る。
- `==強調したい語句==` → 黄色マーカーのハイライト
- `++強調したい語句++` → ブランドカラーの下線
- `**太字**` → 標準の強調(すでにブランドカラーで装飾済み)
- `~~誤り・古い情報~~` → 打ち消し線(訂正・古い情報の明示に)
- `^^気づき・感情が変わる一文^^` → 文字を大きく・青色にして目立たせる強調(「実は思い込みだった」「これは驚いた」のように、読者の認識が変わる/感情が動く一文にだけ使う。地の文の説明にはつけない)。絵文字(💦😳など)は装飾記法とは別に、地の文にそのまま書いてよい
- `%%出典の信頼性・注意点の一言注記%%` → やや小さめ・控えめな色で表示(0.88em/グレー系)。「なお、この見解は企業運営のコラム記事によるもので〜」のような、本文の主張ではなく出典の性質・留意点を添える一文にのみ使う。**景品表示法の打消し表示規制に配慮し、効果効能等の強調表示を打ち消す注記をこの記法で目立たなくする目的では使わない**(読めなくなるほど小さく・薄くしてはいけない)
- Markdownの表(`| 見出し | 見出し |` 形式)・番号なしリストがそのまま使える(表は比較・まとめ情報がある記事でのみ使用し、無理に入れない)

強調記法は1記事に対して合計3〜4箇所程度を上限とし、全部乗せにしない(ハイライトだらけの記事はかえって読みにくい)。

## サムネイル画像
frontmatterの`thumbnail`(例: `/images/articles/YYYY-MM-DD_テーマ.webp`)は、ホームページ・カテゴリ・検索・ランキングの記事カードと記事ページ上部のヒーロー画像、他記事ページの「関連記事」カード、SNSシェア時のOGP画像に使われる。ライターが画像を用意する必要はない(サイト側で別途生成・設置する運用)。確定稿を渡す際、まだ画像がない場合はfrontmatterに`thumbnail`を書かなくてよい(未設定の記事は関連記事欄で本アイコンの代替表示になる)。

## 図表・データ活用
情報量を増やす目的ではなく、読者の理解を助ける目的でのみ使う。判断基準の優先順位:
1. **比較・違いを説明する場合** → 表(Markdown表)を使う
2. **数値変化・割合・傾向を説明する場合** → グラフ(`charts`)を使う
3. **手順や流れを整理する場合** → リストや表を使う
4. **文章だけで十分理解できる場合** → 無理に図表を追加しない

表を作る場合は情報の羅列ではなく、読者が比較・判断しやすい列構成にする(例: `|項目|特徴|おすすめの人|注意点|`)。

執筆中に信頼できる一次情報(政府統計・大手企業や調査会社の公表調査など)で、記事の主張を裏付ける具体的な数値が見つかった場合、frontmatterに以下の形式で`charts`を提案してよい(採用可否・最終調整は編集長が行う)。`type`は用途に応じて使い分ける。

- `stat`: 単一の割合・人数など、比較対象がない1つの数値を大きく見せる
- (typeを省略): 複数カテゴリの量を比較する棒グラフ
- `pie` または `donut`: 内訳・構成比(合計100%になる項目)を円グラフで見せる。5項目まで(6項目以上は自動的に上位4件+「その他」にまとめられる)
- `prosCons`: メリット/デメリットの比較を色分けした2カラムで見せる

```yaml
charts:
  - afterHeading: "この見出しの直後に挿入(本文の見出しテキストと完全一致させる)"
    type: "stat"   # 単一の数値
    value: "82.7"
    unit: "%"
    label: "何の割合かを説明する短い文"
    source: "調査主体名「調査タイトル」(実施時期・n数があれば併記)"
    sourceUrl: "出典URL"
  - afterHeading: "別の見出し"
    # 棒グラフ(typeを省略)。項目間の量を比較したい場合
    title: "グラフのタイトル"
    data: [{label: "男性", value: 38.5}, {label: "女性", value: 43.6}]
    unit: "%"
    source: "..."
    sourceUrl: "..."
  - afterHeading: "内訳を説明する見出し"
    type: "pie"    # 内訳・構成比(合計約100%になるデータ)
    title: "グラフのタイトル"
    unit: "%"
    data: [{label: "原因A", value: 45}, {label: "原因B", value: 30}, {label: "原因C", value: 25}]
    source: "..."
    sourceUrl: "..."
  - afterHeading: "比較したい見出し"
    type: "prosCons"
    title: "メリット・デメリット比較のタイトル(任意)"
    pros: ["メリット1", "メリット2"]
    cons: ["デメリット1", "デメリット2"]
    # prosConsは出典データではなく本文の整理なのでsource/sourceUrlは不要
```
- 出典は必ず一次情報(官公庁・調査実施企業の公式発表)のURLを明記する。まとめサイトや又聞き情報のみを出典にしない(`prosCons`は出典不要)
- 数値は概数(「約80%」等)であればそのまま概数と明記し、正確な数値であるかのように断定しない
- 何を表すデータか・データの期間・出典を必ず明確にし、グラフを置いただけで終わらせず、読み取るべきポイントを本文でも文章で補足する(画像・グラフだけに情報を依存させない。表はHTML/Markdownで出力されるためSEO・アクセシビリティ上も問題ない)
- 1記事に詰め込みすぎず、本文の主張と直結する統計・比較に絞る(無理に全記事へ追加する必要はない)
- 図表の前後に`:::mascot:::`で一言添えると、読者が図表を理解する案内役として機能する(「マスコットキャラクターの使い方」参照。多用は禁止)

## 内部リンク設計
読者が次に知りたい情報へ自然に移動できるよう、SEO目的だけでなく理解を深める導線として設計する。
- 関連性の高い記事・同じカテゴリ内の記事へリンクする
- 初心者向け記事から詳細記事へ誘導し、詳細記事から基礎記事へ戻れるようにする
- 比較記事の末尾には「この商品が向いている人」の内部リンク導線を必ず入れる(例:「乾燥肌の人はこちら」)

## 商品・サービス紹介の原則
単なる広告記事にしない。メリットだけでなく注意点も書き、過度な購入誘導はしない。ランキング形式では評価基準を明確にする。詳細は`writer`エージェント定義の該当ルールを参照。

## 公開前の品質チェックリスト
編集長・レビューアーの最終チェックに先立ち、ライター自身でも確認する。
- **情報品質**: 内容は正確か、最新情報か、根拠が必要な部分に配慮されているか
- **読みやすさ**: 初心者でも理解できるか、説明書のようになっていないか、適度な改行があるか
- **ブランド体験**: サイトの世界観に合っているか、マスコットが自然に機能しているか
- **SEO**: 検索意図を満たしているか、タイトルと内容が一致しているか、内部リンクが適切か
- **信頼性**: 過度な断定表現・誤解を招く表現がないか
- **独自性**: 他サイトの要約になっていないか、比較・整理・具体例・独自の視点が含まれているか

## 保存ルール
- 下書き段階は `サイト運営\実務\ライター\YYYY-MM-DD_テーマ_v1.md` のようにバージョンを明記して保存する
- 確定稿は編集長がfrontmatter込みで `サイト運営\記事データ\確定稿\YYYY-MM-DD_テーマ.md` に保存する
