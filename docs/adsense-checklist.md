## 背景

Googleアドセンスの審査では「コンテンツの量や質が不十分」という理由で不合格になることがある。本ファイルは、審査(不合格後の再申請を含む)に向けた準備状況を管理する。このサイトはGoogleアドセンスに登録していない。独自ドメインを持たず `https://nevora-lifestyle.vercel.app/` で公開している(独自ドメインへ移す場合の手順は `docs/domain-migration-plan.md` 参照)。

### 2-3. 実質的な中身がないページ(インデックス対象かどうかの確認)

空になりうるページは index させない。

| ページ | 確認すること | 判定 |
|---|---|---|
| `/worry/[slug]` | 各悩みページに記事があり、空にならないか(0件の悩みページは index させない) | |
| 検索結果ページ `/search` | クエリなし/未ヒット時は記事一覧が空になりうる。canonical を`/search`固定にしてクエリ違いの重複は防げるが、空の検索結果状態でもindex対象になっていないか。noindex付与を検討 | |
| **`/compare`(商品・サービス比較)** | 比較対象(`items`)が0件だと「まだ登録されていません」だけの空ページになる。`items.length === 0`の間は`noindex`、`sitemap.xml.js`からも除外する(アフィリエイトリンクを戻したときに自動でindex対象・sitemap掲載に戻る作り) | |
| カテゴリページ(`/category/[name]`) | 生成対象が実記事から動的に集計され、**記事0件のカテゴリは静的パスが生成されない**か(`lib/posts.js`の`getAllCategories()`) | |

- 悩みページ(`/worry/[slug]`)は固定で毎回生成されるため、記事の再構成等で0件になる悩みが出た場合は、`/compare`と同様の対応(noindex・sitemap除外)が必要になる点に留意する

## 3. 技術要件

| 項目 | 確認すること |
|---|---|
| 404ページの存在・品質 | `pages/404.js`が存在し、`noindex`指定があり、カテゴリ一覧・人気記事・検索リンクへの導線があるか |
| リンク切れ(内部リンク) | `content/articles`内の本文から`/posts/xxx`形式の内部リンクを全件抽出し、実在する記事のslugと突き合わせてリンク切れ0件か。記事本文は今後も追加・修正されるため、大きく本文を書き換えるバッチ作業のたびに再チェックが望ましい |
| ads.txt | `public/ads.txt`が設置されているか(このサイトの`public/ads.txt`には設置済み。パブリッシャーIDの値は実物を見る)。Next.jsは`public/`配下を任意のドメインでそのまま配信するため、ドメインが変わっても追加作業なしで有効になる見込み。移行後は実際にアクセスして中身が変わっていないことのみ確認すればよい |
| モバイル表示崩れ | 静的なコード確認のみでは判定できない。**再申請前にGoogle Search Consoleの「モバイルユーザビリティ」またはPageSpeed Insightsでの確認を推奨** |

## 4. 重複コンテンツ

- タグ(`tags`)単位の一覧ページ(`/tags/[tag]`等)があるか。無ければ「タグページ間の実質重複」は発生しない。
- カテゴリページ(10件)と悩みページは、同じ記事が両方に掲載されることがある(1記事が1カテゴリ+複数worryに属せるため)。各ページの`title`/`description`/`canonicalPath`がカテゴリ名・悩み名ごとに動的生成されているか(`pages/category/[name].js`・`pages/worry/[slug].js`)。記事が複数の一覧ページに載ること自体(クロスカテゴライズ)は、AdSense審査における「重複コンテンツ」問題には通常該当しない。
- `/search`ページはクエリ文字列に関わらずcanonicalが`/search`固定か(クエリバリエーションによる重複インデックスの防止。空状態のindex可否は2-3節を参照)。

## まとめ:優先度付き対応候補

対応候補は、上の各節を確かめてから書く。書くときは、項目ごとに優先度(✅対応済み/🟡/🟢)と対応時期を付ける。

- 汎用SVGテキストスキャナ(`NEVORA_SCAN_SVG_TEXT=1`、experimental)の検出(はみ出し・衝突)は、記事専用のハードコードウィジェット側の修正が必要になる。スキャナの衝突検出ロジック自体に誤検知が残っている可能性があるため、ブロッキング化の前提条件(誤検知の解消)が満たされるまではブロッキング化しない
